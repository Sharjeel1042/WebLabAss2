# Smart Campus Service Management API (Assignment 2)

A database-driven REST-style API for managing campus service requests. It is the second stage of the Smart Campus case study: Assignment 1 used the plain Node.js `http` module with a JSON file, and this version uses **Express** for routing and **MongoDB with Mongoose** for storage.

## 1. Assignment requirements and how they are met

| Requirement | Where it is implemented |
|---|---|
| MongoDB collections: Users, ServiceRequests, Categories | `src/models/User.js`, `src/models/ServiceRequest.js`, `src/models/Category.js` |
| Mongoose schema for ServiceRequest | `src/models/ServiceRequest.js` |
| Mongoose model | `module.exports = mongoose.model('ServiceRequest', ...)` in `src/models/ServiceRequest.js` |
| Connect Node.js to MongoDB | `src/config/db.js`, started from `src/server.js` |
| CRUD: create request | `POST /requests` (`createRequest`) |
| CRUD: retrieve all requests | `GET /requests` (`getAllRequests`) |
| CRUD: retrieve request by ID | `GET /requests/:id` (`getRequestById`) |
| CRUD: update request | `PATCH /requests/:id` (`updateRequest`) |
| CRUD: delete request | `DELETE /requests/:id` (`deleteRequest`) |
| At least one aggregation query | `GET /requests/stats/unresolved-by-category` (`getUnresolvedByCategory`) |
| Express replaces manual routing | `src/app.js`, `src/routes/*` |
| Middleware | `src/middleware/validateObjectId.js`, `src/middleware/errorHandler.js` |
| Routers and controllers | `src/routes/*`, `src/controllers/*` |
| Handle invalid URLs and invalid IDs | `notFound` (404) and `validateObjectId` (400) |

### Layer responsibilities

- **Routes** map URLs and HTTP methods to controller functions. They contain no logic.
- **Middleware** runs before controllers. It validates IDs and handles errors.
- **Controllers** contain the request logic and talk to the models.
- **Models** define the shape of each collection and its validation rules.
- **Config** handles the database connection.

## 3. Data model

### Users
| Field | Type | Rules |
|---|---|---|
| `_id` | ObjectId | generated by MongoDB |
| `name` | String | required, max 100 characters |
| `email` | String | required, unique, lowercased, must match a basic email format |
| `role` | String | `student` or `staff` |
| `createdAt`, `updatedAt` | Date | added automatically |

### Categories
| Field | Type | Rules |
|---|---|---|
| `_id` | ObjectId | generated by MongoDB |
| `name` | String | required, unique, max 80 characters |
| `description` | String | optional |

### ServiceRequests
| Field | Type | Rules |
|---|---|---|
| `_id` | ObjectId | this is the **Request ID** from the assignment |
| `requester` | ObjectId -> User | required (Student/Staff) |
| `category` | ObjectId -> Category | required |
| `description` | String | required, 10 to 1000 characters |
| `priority` | String | `Low`, `Medium` (default), or `High` |
| `status` | String | `Open` (default), `In Progress`, or `Resolved` |
| `date` | Date | defaults to the time of creation |
| `createdAt`, `updatedAt` | Date | added automatically |

MongoDB has no foreign keys, so the application checks that the requester and category exist before creating a request.

## 4. Setup

### Requirements
- Node.js 18 or newer (check with `node -v`)
- A MongoDB database: MongoDB Atlas (cloud) or a local MongoDB server
- MongoDB Compass (optional, for viewing the data)

### Steps

1. Open a terminal in the project folder.
2. Install the packages:
   ```bash
   npm install
   ```
3. Create your environment file by copying the template:
   ```bash
   copy .env.example .env        # Windows
   cp .env.example .env          # macOS / Linux
   ```
4. Open `.env` and set your connection string:
   ```
   MONGODB_URI=mongodb+srv://<username>:<password>@<cluster-url>/smart_campus?retryWrites=true&w=majority
   PORT=3000
   ```
   If your password contains special characters such as `@` or `#`, URL-encode them (for example `@` becomes `%40`).
5. In MongoDB Atlas, make sure your current IP address is allowed under **Network Access**.
6. (Optional) Load sample data:
   ```bash
   npm run seed
   ```
7. Start the server:
   ```bash
   npm run dev       # restarts automatically when files change
   # or
   npm start         # runs once
   ```

You should see:
```
MongoDB connected
Server running on http://localhost:3000
```

| `npm run dev` | `nodemon src/server.js` | run with auto-restart during development |
| `npm run seed` | `node src/seed/seed.js` | clear and refill the sample data |

## 5. API reference

Base URL: `http://localhost:3000`

All responses are JSON. Successful responses have `"success": true` and a `data` field. Errors have `"success": false` and an `error` message.

### Health check
`GET /`  
Returns `200` with a confirmation message.

### Users
| Method | URL | Description | Success |
|---|---|---|---|
| GET | `/users` | List users. Optional filter: `?role=student` or `?role=staff` | 200 |
| GET | `/users/:id` | Get one user | 200 |
| POST | `/users` | Create a user | 201 |

Example body for `POST /users`:
```json
{ "name": "Ayesha Khan", "email": "ayesha@campus.edu", "role": "student" }
```

### Categories
| Method | URL | Description | Success |
|---|---|---|---|
| GET | `/categories` | List categories, sorted by name | 200 |
| GET | `/categories/:id` | Get one category | 200 |
| POST | `/categories` | Create a category | 201 |

Example body for `POST /categories`:
```json
{ "name": "Electrical", "description": "Power and lighting problems" }
```

### Service requests
| Method | URL | Description | Success |
|---|---|---|---|
| GET | `/requests` | List requests, newest first. Optional filters: `status`, `priority`, `category` | 200 |
| GET | `/requests/:id` | Get one request, with requester and category details | 200 |
| POST | `/requests` | Create a request | 201 |
| PATCH | `/requests/:id` | Update `description`, `priority`, `status`, or `category` | 200 |
| DELETE | `/requests/:id` | Delete a request | 200 |
| GET | `/requests/stats/unresolved-by-category` | Count unresolved requests per category (aggregation) | 200 |

Example body for `POST /requests`:
```json
{
  "requester": "<user _id>",
  "category": "<category _id>",
  "description": "Wi-Fi keeps disconnecting in the CS lab",
  "priority": "High"
}
```

Example body for `PATCH /requests/:id`:
```json
{ "status": "Resolved" }
```

Example response from `GET /requests/stats/unresolved-by-category`:
```json
{
  "success": true,
  "data": [
    { "categoryId": "65f1...", "categoryName": "IT Support", "unresolvedCount": 2 },
    { "categoryId": "65f2...", "categoryName": "Maintenance", "unresolvedCount": 2 },
    { "categoryId": "65f3...", "categoryName": "Library", "unresolvedCount": 1 }
  ]
}
```

### Aggregation pipeline (unresolved-by-category)

| Stage | Purpose |
|---|---|
| `$match` | keep requests where `status` is not `Resolved` |
| `$group` | group by `category` and count |
| `$lookup` | join with the `categories` collection to get the name |
| `$unwind` | turn the joined array into one object |
| `$project` | choose the output fields |
| `$sort` | largest counts first |

### Error responses

| Situation | Status | Example `error` message |
|---|---|---|
| Malformed ID in the URL | 400 | `Invalid request ID: "abc"` |
| Missing required field | 400 | `Description is required` |
| Field value too short, too long, or not in allowed list | 400 | `Description must be at least 10 characters` |
| Requester or category does not exist | 400 | `Requester not found` |
| Malformed JSON body | 400 | `Malformed JSON in request body` |
| Nothing valid to update | 400 | `No valid fields provided to update` |
| Document not found | 404 | `Service request not found` |
| Unknown URL | 404 | `Route not found: GET /banana` |
| Duplicate unique value (email, category name) | 409 | `email already exists` |
| Unexpected server error | 500 | `Something went wrong on the server` |

## 6. Testing with curl (Command Prompt or Git Bash)

```bash
# Create a request (replace the IDs with real ones from GET /users and GET /categories)
curl -X POST http://localhost:3000/requests -H "Content-Type: application/json" -d "{\"requester\":\"<userId>\",\"category\":\"<categoryId>\",\"description\":\"Projector not working in room B-204\",\"priority\":\"High\"}"

# List all requests
curl http://localhost:3000/requests

# Filter by status
curl "http://localhost:3000/requests?status=Open"

# Get one request
curl http://localhost:3000/requests/<requestId>

# Update status
curl -X PATCH http://localhost:3000/requests/<requestId> -H "Content-Type: application/json" -d "{\"status\":\"Resolved\"}"

# Delete
curl -X DELETE http://localhost:3000/requests/<requestId>

# Aggregation
curl http://localhost:3000/requests/stats/unresolved-by-category

# Error checks
curl http://localhost:3000/requests/abc          # 400: invalid ID
curl http://localhost:3000/banana                # 404: unknown route
```

On PowerShell, use `Invoke-RestMethod` or wrap the JSON in single quotes as needed.

## 7. Design decisions (for the viva)

- **Layered structure.** Routes, controllers, and models each have one job, so each part can be explained and changed separately.
- **Express instead of the raw `http` module.** Routing, JSON parsing, and middleware come from Express. Assignment 1's manual routing shows what Express replaces.
- **Mongoose schemas.** Validation rules (required fields, enums, lengths) live in the models, so every write is checked before it reaches MongoDB.
- **References instead of copied data.** Requests store the requester and category IDs, and `populate` fetches the details. This avoids duplicated names that could go out of date.
- **Application-level relationship checks.** MongoDB does not enforce foreign keys, so the controller confirms the user and category exist.
- **Whitelisted updates.** `updateRequest` only accepts known fields, so clients cannot change internal values such as `_id` or `date`.
- **`runValidators: true` on updates.** Update queries skip schema validation by default, so this option applies the enum and length rules to updates too.
- **`PATCH` for partial updates.** Only the fields sent are changed.
- **Central error handling.** Controllers throw errors and `errorHandler` formats them, so the response format is consistent and internal details are not exposed.
- **Aggregation for counts.** The database does the counting, so the Node process does not load every request into memory.
- **Index on `status` and `category`.** Speeds up the filtered counts as data grows.

## 8. Known limitations

- No authentication. Anyone who can reach the server can create, change, or delete data. Authentication is the topic of Assignment 3.
- No pagination on `GET /requests`. Fine for this assignment, but a large dataset would need `limit` and `skip`.
- Requests cannot be created for a user or category that does not exist, but deleting a user or category does not delete or update the requests that reference it.
